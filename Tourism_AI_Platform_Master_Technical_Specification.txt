======================================================================
1. EXECUTIVE SUMMARY
======================================================================

Tourism AI Platform is a multi-layer artificial-intelligence platform
for tourism. It is not merely a dashboard and Tourism Pulse is not the
whole product.

The platform combines three core intelligence models:

1. Traveler DNA
   Models who a traveler is, how they travel, what they prefer, and how
   their behavior changes.

2. Tourism Pulse
   Models what is happening in a destination now: demand, capacity,
   events, environment, confidence, trends and anomalies.

3. Destination Twin
   Models the destination itself: geography, infrastructure, tourism
   assets, businesses, visitor flows, economic activity, environment,
   events, constraints and scenarios.

These three models feed a shared Tourism Knowledge Graph.

The Knowledge Graph feeds an AI Agent layer containing, initially:

- Traveler Agent
- Business Agent
- City Agent

Additional specialized agents can later be added.

All of this is exposed through Tourism Studio, the operating environment
for travelers, tourism businesses, destination authorities and other
professional users.

The platform therefore follows:

DATA
  ->
SIGNALS
  ->
INTELLIGENCE MODELS
  ->
KNOWLEDGE GRAPH
  ->
AI AGENTS
  ->
TOURISM STUDIO
  ->
DECISIONS / ACTIONS

The existing Tourism Pulse implementation is the first working analytical
subsystem of this larger architecture.

4. ARCHITECTURAL PRINCIPLES
======================================================================

4.1 Evidence before intelligence

AI must not be the source of truth for quantitative tourism metrics.

Raw evidence is collected first. Deterministic analytical systems
calculate metrics. AI interprets and acts on those metrics.

4.2 Preserve raw data

Raw observations must remain recoverable.

The transformation chain must be traceable:

SOURCE
  ->
RAW OBSERVATION
  ->
VALIDATED OBSERVATION
  ->
NORMALIZED SIGNAL
  ->
EFFECTIVE SIGNAL
  ->
DIMENSION
  ->
INTELLIGENCE
  ->
AI INTERPRETATION

4.3 Explainability

Every important result must be explainable.

A user asking:

    "Why is Budapest Demand 68?"

must eventually be able to see the underlying signals and their sources.

4.4 Confidence is first-class

Every major intelligence output should communicate confidence and
coverage.

4.5 Time awareness

Tourism data has different frequencies. A monthly government statistic
must not be represented as real-time data.

4.6 Seasonal awareness

Tourism is strongly seasonal. Models must distinguish normal seasonal
behavior from unusual changes.

4.7 Modular domains

Traveler DNA, Tourism Pulse and Destination Twin must remain independent
domains with explicit interfaces.

4.8 Start simple, scale when justified

Do not introduce Kafka, Kubernetes, graph databases or distributed
processing until actual scale or functionality requires them.

4.9 API-first

The platform should expose stable APIs so the same intelligence can be
used by web, mobile, agents and external customers.

4.10 Privacy by design

Traveler data is potentially sensitive. Personalization must use
explicit consent, purpose limitation, access controls and retention
policies.

5. SYSTEM 1 - TRAVELER DNA
======================================================================

5.1 Purpose

Traveler DNA is a dynamic representation of a traveler's preferences,
behavior, history and context.

It is not simply a demographic profile.

5.2 Core model

Traveler
  - traveler_id
  - account_id
  - origin
  - preferred_language
  - travel_party
  - budget_profile
  - created_at
  - updated_at

5.3 Preference dimensions

Examples:

- culture
- food
- nightlife
- beach
- nature
- adventure
- luxury
- family
- business
- wellness
- shopping
- history
- sports

Each preference should have:

- value
- confidence
- evidence_count
- last_updated

5.4 Behavioral attributes

Examples:

- booking_horizon
- average_trip_duration
- average_budget
- price_sensitivity
- weather_sensitivity
- crowd_tolerance
- event_sensitivity
- seasonality
- preferred_transport
- preferred_accommodation

5.5 Traveler history

Possible entities:

- trips
- destinations visited
- attractions visited
- bookings
- searches
- saved destinations
- recommendations accepted
- recommendations rejected

5.6 Dynamic DNA

Traveler DNA must evolve from behavior.

Example:

Initial:
    culture = 0.60
    nightlife = 0.40

After repeated cultural trips:
    culture = 0.82

The system must preserve the evidence behind changes.

5.7 Privacy

Traveler DNA requires:

- explicit consent
- data minimization
- purpose limitation
- deletion capability
- export capability
- encryption
- strict tenant isolation
- audit logging

No sensitive personal attribute should be inferred merely because it is
technically possible.


======================================================================
6. SYSTEM 2 - TOURISM PULSE
======================================================================

6.1 Purpose

Tourism Pulse answers:

    "What is happening in a destination now?"

6.2 Core dimensions

Demand
Capacity
Events
Environment

Initial weights:

Demand       0.35
Capacity     0.25
Events       0.20
Environment  0.20

Weights must eventually be configurable.

6.3 Signal model

A signal contains:

- place_id
- signal_type
- value
- unit
- observed_at
- source
- source reliability
- metadata

Examples:

- tourism_nights
- hotel_occupancy
- airport_arrivals
- flight_capacity
- search_interest
- sentiment
- weather_comfort
- precipitation
- event_count

6.4 Signal processing

normalized_value = source-specific normalization(value)

freshness = 0.5 ^ (age_hours / half_life_hours)

effective_signal =
    normalized_value
    * freshness
    * reliability

6.5 Reliability

Current baseline:

government    1.00
official      1.00
airport       0.98
airline       0.98
hotel         0.95
booking       0.95
commercial    0.90
news          0.85
social        0.65
unknown       0.40

Source-specific values should eventually be managed through a source
registry.

6.6 Confidence

Confidence should incorporate:

- source reliability
- freshness
- dimension coverage
- consistency
- historical stability

The current implementation uses a simpler confidence model and should
evolve incrementally.

6.7 Coverage

Coverage = supported dimensions / total dimensions

Example:

Demand       supported
Capacity     missing
Events       missing
Environment  supported

Coverage = 2 / 4 = 50%

Coverage must be displayed rather than hidden.

6.8 Historical snapshots

Pulse snapshots contain:

- place_id
- calculated_at
- pulse
- demand
- capacity
- events
- environment
- confidence_score
- confidence_coverage

6.9 Trend

Trend states must distinguish:

UP
DOWN
STABLE
UNKNOWN / INSUFFICIENT_HISTORY

A zero numeric change must not automatically mean stable.

6.10 Anomaly

Anomaly detection should eventually support:

- statistical anomaly
- seasonal anomaly
- dimension anomaly
- source anomaly
- composite anomaly

6.11 Existing implementation status

Already implemented in the current repository:

- FastAPI API
- SQLAlchemy models
- signal processing
- normalization
- freshness
- reliability
- effective signals
- dimensions
- Pulse calculation
- confidence
- interpretation
- events
- snapshots
- history
- trend
- anomaly endpoints
- React/Vite dashboard
- extensive tests

This subsystem is the current technical foundation, not the complete
Tourism AI Platform.

15. DATA LINEAGE
======================================================================

Every derived value should eventually have a lineage chain.

Example:

    Pulse = 57.2
      ->
    Demand = 68.4
      ->
    tourism_nights signal
      ->
    KSH observation
      ->
    KSH source file
      ->
    source URL

The UI should eventually support:

    "Why is this number what it is?"


======================================================================
16. FORECASTING
======================================================================

Forecasting is a later intelligence layer.

Potential outputs:

- next day Pulse
- next week Pulse
- next month demand
- seasonal forecast
- event impact forecast

Every forecast should include uncertainty.

Example:

    Forecast = 63.2
    Expected range = 57-69
    Confidence = 82%

Forecasting should use historical snapshots, signals, seasonality,
events and external variables.

======================================================================

Potential tourism risks:

- demand collapse
- capacity shortage
- overcrowding
- weather
- transport disruption
- event cancellation
- economic shock
- geopolitical disruption

    probability
    x
    impact

======================================================================
18. RECOMMENDATION ENGINE
======================================================================

Recommendations must be evidence-backed.

Example:

    Demand is weakening.
    Confidence = 81%.
    Main evidence:
      - airport arrivals down
      - hotel occupancy down
      - search interest down

    Recommendation:
      monitor for another period before changing capacity.

Recommendations should distinguish:

- observation
- inference
- prediction
- recommendation

48. NON-FUNCTIONAL REQUIREMENTS
======================================================================

Reliability:
    APIs should degrade gracefully when sources fail.

Accuracy:
    Raw data and calculations must be deterministic and reproducible.

Explainability:
    Major intelligence results must be traceable to evidence.

Freshness:
    Each signal must expose its observation time and freshness state.

Security:
    Personal and tenant data must be isolated.

Scalability:
    Architecture must permit horizontal API and worker scaling.

Maintainability:
    Domain logic must be independent from UI and HTTP frameworks.

Testability:
    External sources must be mockable.

Observability:
    Every ingestion and intelligence pipeline must be measurable.

Cost control:
    AI calls must be measurable and bounded.


======================================================================
49. ARCHITECTURAL RISKS
======================================================================

Risk:
    Overengineering too early.

Mitigation:
    Start with PostgreSQL and modular Python services.

Risk:
    AI hallucination.

Mitigation:
    Evidence-grounded agents and deterministic analytical core.

Risk:
    Poor data quality.

Mitigation:
    Validation, provenance, confidence and quarantine.

Risk:
    Seasonal bias.

Mitigation:
    seasonal baselines and historical comparison.

Risk:
    Privacy problems.

Mitigation:
    consent, minimization and strict access controls.

Risk:
    Source dependency.

Mitigation:
    adapter architecture and multiple sources.

Risk:
    Graph complexity.

Mitigation:
    relational graph first, dedicated graph later.

Risk:
    Infrastructure complexity.

Mitigation:
    scale architecture only when actual usage requires it.


======================================================================
50. IMPLEMENTATION RULES FOR CODEX / DEVELOPMENT AGENTS
======================================================================

1. Read the architecture specification before implementing major domains.

2. Do not treat Tourism Pulse as the whole application.

3. Preserve explicit domain boundaries.

4. Never hardcode external source data into production logic.

5. Preserve raw observations.

6. Every derived signal must be reproducible.

7. Every external source requires an adapter.

8. External calls must be isolated and mockable.

9. Do not put business logic in FastAPI routers.

10. Do not put domain calculations directly into React components.

11. Maintain API contracts.

12. Add migrations for schema changes.

13. Add tests for every domain behavior.

14. Do not introduce infrastructure technologies without a demonstrated
    requirement.

15. Do not expose personal data to LLMs unless required, authorized and
    properly protected.

16. AI agents must use explicit tools and permissions.

17. AI must not replace deterministic calculations.

18. Any recommendation should expose supporting evidence.

19. Maintain backward compatibility for public APIs where practical.

20. Update architecture documentation when major boundaries change.
